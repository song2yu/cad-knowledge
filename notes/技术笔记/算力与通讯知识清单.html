01

核心概念

Foundation concepts

算力（Compute）

定义：硬件每秒能完成的浮点运算次数，单位 FLOPS（每秒浮点运算数）。常用量级：TFLOPS（10¹²）、PFLOPS（10¹⁵）。

指标含义典型值（参考）
FP32 算力单精度浮点，科学计算/精确仿真A100 ~19.5 TFLOPS
TF32/FP16/BF16半精度/混合精度，深度学习主力A100 ~312 TFLOPS（FP16 + Tensor Core）
FP88-bit 浮点，新一代训练/推理H100 ~1979 TFLOPS（FP8）
INT88-bit 整数，量化推理约为 FP16 的 2 倍

通讯带宽（Bandwidth）与延迟（Latency）

带宽：单位时间能传输的数据量（GB/s），决定「搬数据多快」；延迟：一次通讯的启动开销（μs 级），决定「叫一次人要多久」。小消息看延迟，大块数据看带宽——这是理解一切通讯优化的起点。

计算强度与瓶颈判定（Roofline 模型）

算术强度 Arith. Intensity = 计算量 FLOPs / 访存量 Bytes（单位：FLOP/Byte）
Compute-bound

算力瓶颈

算术强度高于机器「平衡点」（峰值算力 ÷ 带宽）。典型：大矩阵乘（GEMM）、CNN 卷积。提升算力（更多卡、更高精度加速）有效。

Memory-bound

带宽瓶颈

算术强度低，大部分时间在搬数据。典型：LLM 解码（逐 token 生成）、softmax、归一化层。此时堆算力无效，提升显存带宽/减少数据搬运才有效。

关键认知：LLM 推理的 decode 阶段几乎总是带宽瓶颈（每生成一个 token 要把全部参数读一遍），这就是为什么推理速度常以「显存带宽 ÷ 模型大小」估算，而不是算力。训练阶段整体偏算力瓶颈，但梯度同步、优化器步骤仍大量受通讯/带宽制约。

单机多卡通讯

Intra-node communication

通讯原语（NCCL 实现）

原语行为数据量（每卡）典型用途
Broadcast一张卡发给所有卡全量广播参数初始化
AllReduce所有卡的数求和/平均，结果人人都有~2× 数据量（Ring）数据并行梯度同步
AllGather每人一份碎片，拼成完整数据人人都有~(N-1)/N × 全量ZeRO/FSDP 前向拉参数
ReduceScatter求和后按碎片分发~(N-1)/N × 全量ZeRO/FSDP 梯度归约
P2P（Send/Recv）点对点直传指定块流水线并行的激活传递

Ring AllReduce 的关键性质

通讯时间 ≈ 2(N-1)/N × 数据量 / 带宽（N = 卡数）
  • 带宽最优：每卡只需收发约 2(N-1)/N × 数据量，与卡数近似无关（卡多时趋近 2× 数据量）。
  • 延迟敏感：分 2(N-1) 步，步数随卡数线性增长——小消息场景下延迟占主导。
  • 这就是「梯度分桶（bucketing）」的原因：把小梯度攒成大桶，用满带宽、摊薄延迟。

单机多卡的关键事实

好消息：机内有 NVLink/NVSwitch 时，AllReduce 通讯开销通常能被计算掩盖（重叠），数据并行扩展效率高（8 卡常达 90%+）。
坏消息：若无 NVLink、走 PCIe P2P，卡间带宽骤降至 ~1/14，梯度同步可能占训练时间 30% 以上；若 P2P 被禁用还会绕行 CPU 内存（穿透），雪上加霜。
04

多机通讯

Inter-node communication

与机内的三大差异

差异一

带宽低一个量级

机内 NVLink ~450 GB/s vs 跨机 IB ~50 GB/s。同样的 AllReduce，跨机慢约 9 倍，通讯更难被计算掩盖。

差异二

延迟与抖动

跨机多经过网卡、交换机，延迟更高且有网络抖动；同步式训练中「最慢的机器」决定整体节奏（木桶效应）。

差异三

故障率

长训任务中网卡/链路故障概率显著上升，需要容错：梯度压缩容忍、备份节点、快速 checkpoint 恢复。

多机通讯的核心优化手段

  • 分层归约（Hierarchical AllReduce）：先机内 NVLink 归约，再跨机一次归约，最后机内广播——把跨机流量压到最低。
  • 梯度压缩：FP16/BF16 梯度、量化（如 8-bit）+ 误差补偿，减少跨机字节数。
  • 通讯-计算重叠：梯度分桶、反向传播边算边发，把通讯藏进计算时间里。
  • 梯度累积：本地累积多步再同步一次，用「牺牲等效 batch 精细度」换通讯次数。
  • Overlap + 异步：本地 SGD/异步 SGD 减少等待，但引入梯度陈旧（staleness），收敛需调参。
部署法则：通讯频繁的并行维度（张量并行）放机内；通讯稀疏的维度（流水线、数据并行）放机间。这就是大模型训练「3D 并行」的排布铁律。

❓ 深入问答：机间通讯靠什么？瓶颈是带宽吗？

Q1

机间通讯靠什么实现？

靠 网络互联，分三个层次：

  • 物理链路：网卡（NIC/HCA）+ 交换机 + 光模块/铜缆。主流两种协议栈——InfiniBand（IB）（专用网络，HPC/大模型集群标配）与 RoCEv2（在以太网上承载 RDMA，成本更低）。
  • 传输机制：核心是 RDMA（远程直接内存访问）——GPU/NIC 直接读写对端内存，绕过 CPU 和操作系统内核，实现零拷贝、低延迟、低 CPU 占用。没有 RDMA 的普通 TCP 通讯，延迟高一个量级且 CPU 被打满。
  • 集合通讯库：上层由 NCCL（NVIDIA）或 Gloo/MPI 把 AllReduce/AllGather 等原语映射到 IB/RoCE 链路上，并自动做「机内 NVLink 归约 → 跨机 IB 归约 → 机内广播」的分层优化。
Q2

瓶颈是带宽吗？—— 分场景，不能一概而论

大消息场景（如全量梯度 AllReduce）：瓶颈就是带宽。数据量大到延迟可忽略，耗时 ≈ 数据量 ÷ 跨机带宽。此时提升带宽（IB HDR→NDR、多网卡聚合、梯度压缩）直接见效。

小消息场景（如 TP 每层 AllReduce、MoE 的 All-to-All 小包）：瓶颈是延迟，不是带宽。消息小到带宽根本跑不满，耗时由「每次通讯的固定启动开销 × 通讯次数」决定。此时加带宽几乎无效，要靠减少通讯次数（算子融合、增大 batch、梯度累积）或降低单次延迟（RDMA、拓扑优化）。

场景主导瓶颈判定依据有效对策
数据并行梯度 AllReduce（大模型）带宽消息大（GB 级），延迟占比可忽略IB 升级、梯度压缩、分层归约、通讯重叠
张量并行每层 AllReduce延迟消息小（KB-MB 级），每层都发放机内 NVLink、算子融合、减少层数通讯
MoE 专家 All-to-All带宽 + 负载不均流量大且分布倾斜，热点链路拥塞专家负载均衡、EP 放机内、自适应路由
流水线并行激活传递延迟（+ 气泡）P2P 小消息，且受流水线气泡影响增大 micro-batch、交错调度、减少阶段数
ZeRO-3 参数 AllGather带宽每层前后向都要拉全量参数降级 ZeRO-2、参数分桶调大、机内优先
一句话结论：机间通讯靠 RDMA over InfiniBand / RoCE 实现；瓶颈大消息看带宽、小消息看延迟。更准确地说，真实瓶颈往往是「带宽 × 延迟 × 通讯次数」三者中最短板的那一个——所以优化前必须先判断消息大小与通讯频率，否则容易优化错方向。
补充：还有两个常被忽略的机间瓶颈
① 网络拓扑与拥塞：Fat-Tree / Dragonfly 拓扑下，多对多通讯可能撞上同一上行链路，实际带宽远低于理论值；自适应路由（SHARP、Adaptive Routing）可缓解。
② 掉队者（straggler）与抖动：同步训练中，任一节点网络抖动或算力偏慢，全体等待。此时瓶颈既不是带宽也不是延迟，而是最慢节点的响应时间。

Parallelism & communication patterns
策略切什么通讯内容通讯频率通讯量适合位置
DP 数据并行数据梯度（AllReduce）每步 1 次（反向末）大（全量梯度）机间可接受（可重叠）
ZeRO-1/2/3 / FSDP优化器状态/梯度/参数AllGather + ReduceScatter每层前后向中（分片摊薄）机内为主，机内+IB 亦可

PP 流水线并行按层切阶段阶段边界激活（P2P）稀疏（阶段边界）小（仅激活）机间友好
SP 序列并行序列维度AllGather/ReduceScatter（注意力区）每层注意力处中常与 TP 同域（机内）
EP 专家并行MoE 专家All-to-All（token 分发/回收）每 MoE 层 2 次大且不均机内优先，IB 需高带宽

组合拳：3D / 5D 并行

大模型训练的标准排布：TP + SP 放机内（NVLink 域）→ PP 跨机（IB，通讯稀疏）→ DP/ZeRO 最外层（跨机，可重叠）。以 GPT-3 175B 级别训练为例，典型配置为 8 卡机内 TP×8 或 TP×4+PP，跨机 DP 数十至上百路。

TP 跨机的代价：TP 每层要 2 次 AllReduce（前向 + 反向），跨机做会让每层都等网络——实测跨机 TP 可让训练速度掉 50% 以上。这就是为什么 TP 几乎从不跨机。

对训练的影响

Impact on training

扩展效率（Scaling Efficiency）

理想加速比 = 卡数 N；实际加速比 = N × 扩展效率
  • 通讯占比：通讯时间 / 总时间。机内 NVLink + 大 batch 下通常 <10%；跨机 + 小 batch 可达 30-50%。
  • 木桶效应：同步训练中任一卡慢/网络抖动，全体等待。长训中「掉队者（straggler）」是吞吐杀手。
  • 显存-通讯权衡：ZeRO-3/FSDP 省显存但增加 AllGather 通讯（每层前后向都要拉参数）；offload 到 CPU 省更多显存但 PCIe 带宽成为新瓶颈。

常见现象与根因

现象根因对策
加卡后速度不成比例梯度同步通讯占比上升 / batch 太小增大 batch、梯度累积、分层归约
多机比多卡慢得多跨机带宽低 + TP 误放机间重排并行维度：TP 机内、PP 机间
GPU 利用率忽高忽低数据加载 IO 瓶颈 / 掉队卡预取、DALI/GDS、排查慢节点
ZeRO-3 反而变慢参数 AllGather 通讯增加换 ZeRO-2、参数分桶调大、机内 NVLink
MFU 上不去（<40%）小算子多、通讯碎片化、非 GEMM 占比高算子融合、flash attention、更大矩阵
经验法则：大模型训练 MFU（模型算力利用率）健康区间约 35%–55%。低于 30% 通常意味着通讯/IO/小算子出了问题，先查通讯再查数据管道。

对推理的影响

Impact on inference

两个阶段的瓶颈完全不同

Prefill 阶段

算力瓶颈（compute-bound）

整段 prompt 一次性并行计算，矩阵乘大、算术强度高。堆算力（多卡 TP）直接提速，通讯可被计算掩盖。

Decode 阶段

带宽瓶颈（memory-bound）

逐 token 生成，每步都要读全部参数 + KV Cache，算术强度 ≈ 1-2 FLOP/Byte。速度 ≈ 显存带宽 ÷ (参数量 + KV Cache)。

多卡推理的权衡

  • TP（张量并行）：把参数切到多卡 → 每卡读取量变小 → decode 提速近似线性；但每层要 2 次 AllReduce，通讯延迟直接加进每个 token 的生成时间。机内 NVLink 下收益显著；跨机则延迟反噬收益。
  • PP（流水线并行）：通讯少，但 decode 阶段流水线「气泡」明显（各阶段轮流空闲），单请求延迟变差，只适合提吞吐（大 batch）。
  • KV Cache 是隐形杀手：长上下文时 KV Cache 可达数十 GB，既挤占显存（限制 batch）又拖慢 decode（访存量暴涨）。对策：PagedAttention、GQA/MQA、KV 量化。
  • 吞吐 vs 延迟：增大 batch 提升吞吐（算力利用率变高），但单请求延迟上升。在线服务常做「连续批处理（continuous batching）」动态平衡。
实用估算：decode 速度（token/s）≈ 显存带宽 ÷（模型参数字节数 + KV Cache 字节数）。例：70B 模型 FP16（140 GB）在 3.35 TB/s 的 H100 上单卡放不下；TP=2 后每卡 ~70 GB + KV，理论 ~40 token/s 量级——这就是「推理吃带宽、训练吃算力」的直观体现。
通讯对推理的影响一句话：训练时通讯藏在步与步之间，可以重叠；推理 decode 时通讯直接串在每 token 的关键路径上——每层 AllReduce 的延迟（哪怕只有几十 μs）乘以层数，就是每个 token 的固定开销。这是「推理 TP 不宜跨机」的根本原因。

调优检查清单

  1. 先测瓶颈：nvidia-smi 看 SM 利用率与显存带宽；Nsight/PyTorch Profiler 看通讯占比——是算力、带宽、通讯还是 IO 瓶颈，对症下药。
  2. 通讯占比 >20%：增大 batch / 梯度累积 / 分层归约 / 梯度压缩 / 检查并行维度排布。
  3. TP 是否跨机了：跨机 TP 是性能事故，立即重排为「TP 机内 + PP 机间」。
  4. 推理慢：先判断 prefill 还是 decode 慢；decode 慢优先查 KV Cache 大小与显存带宽利用率，再考虑 TP/量化。
  5. 多机不稳：检查网卡拓扑（ibstat/nvidia-smi topo）、RDMA 配置、是否有掉队节点。
  6. 省显存还是省通讯：ZeRO-2 → ZeRO-3 → offload 是「显存换通讯/带宽」的阶梯，按需逐级启用。
一句话总结：训练是「算力 + 可隐藏的通讯」，推理是「带宽 + 串行路径上的通讯」。理解每个操作是算力瓶颈还是带宽瓶颈、通讯在关键路径上还是可以重叠，就掌握了 90% 的性能调优判断力。
